# User 도메인 모델

- Status: Active
- Audience: Engineers
- Source of Truth: Yes
- Last Reviewed: 2026-09-08

## 도메인 개요

User 도메인은 **서비스를 이용하는 일반 사용자의 계정 생명주기, 식별 정보, 자격 증명과 프로필을 관리**하는 도메인입니다. 시스템 전반에서 주체가 되는 사용자 개념을 정의하고 계정과 프로필 변경 규칙을 캡슐화합니다.

### 목적

- 서비스 내의 일반 사용자를 고유하게 식별하고 인증할 수 있는 계정 기반을 제공한다.
- 회원가입, 이메일 검증과 비밀번호 재설정의 일관된 계정 생명주기를 보장한다.
- 닉네임과 선택된 아바타 캐릭터 식별자의 변경 규칙을 도메인 객체(`User`) 내에 캡슐화하여 일관성을 보장한다.
- 앞뒤 공백을 제거한 닉네임의 길이(1~20자), 이메일 형식 등 값 객체(Value Object)를 통해 입력 데이터의 정합성을 보장한다.

### 핵심 책임

- 사용자 계정 등록, 로그인 가능 상태, 프로필 수정과 회원 탈퇴 관리
- 이메일 검증과 비밀번호 재설정 정책 관리
- 이메일과 비밀번호를 포함한 자격 증명 변경 규칙 관리
- 닉네임 점유(`NicknameHold`) 메커니즘: 중복 확인 시점부터 수정 확정까지 일정 시간 동안 닉네임을 점유하여 동시 요청에 의한 충돌 방지
- 캐릭터 식별자(`characterId`)를 필수 프로필 상태로 저장하고 변경
- 외부 프로필 응답이 필요할 때 Character 공개 계약으로 이미지 참조를 일괄 해석
- `NicknamePolicy` 도메인 서비스를 통한 닉네임 점유 만료 정책 관리
- 닉네임 키워드 기반 사용자 검색

### 도메인 경계

- **Aggregate Root**: `User`
- `Email`, `Nickname`은 `User` 내의 Value Object로, 자체 유효성 규칙을 가지며 `User` 없이 독립 존재하지 않는다.
- `NicknamePolicy`는 닉네임 점유 만료 여부 판단 로직을 분리한 **도메인 서비스**이다.
- 닉네임 점유 저장은 User Application의 `NicknameHoldPort` 뒤에 있으며, 현재 운영 Adapter는 단일 인스턴스의 인메모리 저장을 사용한다.
- 계정 등록, 이메일 검증, 비밀번호 재설정과 로그인 가능 상태는 User 모델이 보호하는 계정 생명주기에 속한다.
- 비밀번호 해시, 토큰 생성·검증, 보안 필터, 쿠키와 세션 저장 기술은 User 모델의 책임이 아니다.
- 이메일 검증 기록은 User 모델이 소유하며, 가입 또는 비밀번호 재설정 목적과 사용 여부를 보호한다.
- User는 현재 선택된 캐릭터의 식별자만 소유한다. 캐릭터 유형, 소유자와 이미지 참조의 의미 및 자산 생명주기는 Character가 소유한다.
- User Application은 자신이 소유한 출력 포트로 사용자 식별자와 캐릭터 식별자 쌍을 Character 공개 일괄 조회 계약에 전달하며 Character의 Domain·Persistence 모델을 직접 조회하지 않는다.
- `UserAvatarReference`는 User Aggregate의 상태나 저장 경로가 아니라 Character가 해석한 이미지 참조와 접근 속성을 변경 없이 전달하는 Application 조회 모델이다.
- User는 고정 캐릭터 접두사 추가, 레거시 경로 변환, 파일명 기반 유형 추론과 공개 여부 판정을 수행하지 않는다.
- 저장된 캐릭터 식별자를 해석할 수 없으면 null이나 과거 경로로 대체하지 않고 데이터 정합성 오류로 요청을 실패시킨다.

### 프로필 접근 정책

- 프로필 미리보기 조회는 인증 없이 수행할 수 있다.
- 프로필 상세 조회는 인증된 사용자만 수행할 수 있다.
- 프로필 수정과 프로필 이미지 변경은 본인만 수행할 수 있다.
- User 프로필 모델은 식별 정보, 닉네임과 선택된 캐릭터 식별자만 소유한다.
- 일기 수, 월별 기록과 사진 모아보기는 User 모델의 상태가 아니다.
- 프로필 조회 결과에 포함되는 친구 상태와 본인 여부는 현재 조회 요청자와 프로필 대상 사용자의 관계를 기준으로 결정된다.

## 사용자(User)

_Entity_

### 속성

- `id` : String (UUID 36자리). 사용자의 고유 식별자
- `email` : String. 로그인 및 식별용 고유 이메일 주소
- `password` : String. 해시 암호화 처리된 사용자 비밀번호
- `nickname` : String. 서비스 내에서 다른 사람에게 보여지는 고유한 표시 이름
- `characterId` : Long. 현재 아바타로 선택한 캐릭터 식별자
- `createdAt` : LocalDateTime. 최초 가입/생성 일시
- `updatedAt` : LocalDateTime. 최종 수정 일시
- `deletedAt` : LocalDateTime. `User`가 소유하는 회원 탈퇴 처리 일시

### 행위

- `changeNickname(String newNickname)` : 입력을 `Nickname` 값 객체로 변환하여 닉네임을 변경한다.
- `changeNickname(Nickname newNickname)` : 검증된 `Nickname` 값 객체로 닉네임을 변경한다.
- `changeCharacter(Long characterId)` : 현재 아바타 캐릭터 식별자를 변경한다.
- `updatePassword(String newHashedPassword)` : 암호화된 새로운 비밀번호로 변경한다.
- `withdraw()` : 사용자를 회원 탈퇴 처리하고 `deletedAt`을 현재 시각으로 설정한다.
- `isWithdrawn()` : 회원 탈퇴 처리된 사용자인지 여부를 반환한다.

### 규칙

- 이메일(`email`)과 닉네임(`nickname`)은 전체 시스템에서 고유해야 하며 반드시 존재해야 한다.
- `characterId`는 반드시 존재하는 양수이며 데이터베이스에서는 NOT NULL로 유지한다.
- 현재 회원가입과 프로필 변경은 고정 캐릭터를 검증해 선택하지만 User Aggregate의 저장 참조는 캐릭터 생성 유형을 구분하지 않는다.
- 회원가입 Application은 고정 캐릭터의 이미지 Object Key를 반환받지 않고 회원가입에서 선택 가능한 고정 캐릭터인지 여부만 확인한다.
- 사용자 객체의 상태 변경(비밀번호, 닉네임, 캐릭터 식별자 등)은 캡슐화된 메서드를 통해서만 제어되어야 한다.
- 회원 탈퇴는 물리적 완전 삭제 대신 `User`가 소유한 `deletedAt` 값을 갖는 논리적 삭제 구조로 처리한다.
- User와 Character 사이에는 데이터베이스 외래 키를 두지 않으며 Application 경계와 정합성 검사로 참조를 보호한다.

## 닉네임(Nickname)

_Value Object_

### 속성

- `value` : String. 앞뒤 whitespace가 제거된 닉네임 문자열

### 행위

- `Nickname(String value)` : 앞뒤 whitespace를 제거하고 필수 값과 길이를 검증하여 객체를 생성한다.

### 규칙

- 정규화는 Java의 Unicode-aware whitespace 판정에 따라 앞뒤 공백을 제거한다. 중간 whitespace, 대소문자와 기존 문자 정책은 유지한다.
- 정규화된 닉네임은 비어 있지 않은 필수 값이며 길이는 최소 1자에서 최대 20자까지 허용한다. 필수 값이나 길이 조건을 만족하지 않으면 `InvalidNicknameException`이 발생한다.
- 앞뒤 whitespace만 다른 입력은 같은 `Nickname` 값으로 비교된다.

## 이메일(Email)

_Value Object_

### 속성

- `value` : String. 이메일 문자열

### 행위

- `Email(String value)` : 검증 로직을 포함하여 객체를 생성한다.

### 규칙

- 이메일은 비어 있지 않은 필수 값이다.
- 표준 이메일 정규식 패턴(`^[A-Za-z0-9+_.-]+@[A-Za-z0-9.-]+$`)을 통과해야 한다. 조건을 만족하지 않으면 예외가 발생한다.

## 닉네임 점유(NicknameHold)

_Domain Policy와 Application Port_

### 규칙

- 점유 지속 시간은 `NicknamePolicy`가 3분으로 판단한다.
- 닉네임 중복 검사와 점유 Port는 `Nickname` 값 객체를 받는다. 앞뒤 공백 형태가 다른 입력도 동일한 점유 키를 사용한다.
- 동일 사용자는 만료 전 같은 닉네임 점유를 다시 확인할 수 있고, 다른 사용자는 획득할 수 없다.
- 만료된 점유는 다른 사용자가 원자적으로 교체할 수 있다.
- 프로필 저장 성공 후에만 점유를 해제하며 실패 시 재시도를 위해 만료 전까지 유지한다.
- 현재 `ConcurrentHashMap` 기반 Adapter는 단일 애플리케이션 인스턴스에서만 점유를 공유한다.
- 서버 재시작 시 점유가 사라지고 여러 인스턴스 사이에는 공유되지 않는다.
- `users.nickname` 유일 제약은 최종 동시성 방어선이며, 위반은 User의 닉네임 충돌 의미로 번역한다.

## 닉네임 처리 정책

### Application 정책

- 회원가입, 닉네임 사용 가능 확인과 프로필 변경은 Application 진입 시 닉네임을 값 객체로 변환한다. 이후 중복 검사, 점유와 저장에는 정규화된 값을 사용한다.
- 프로필 변경에서 닉네임이 null이면 닉네임 변경 의도가 없다. 빈 문자열과 whitespace만 있는 문자열은 캐릭터 변경이 함께 요청되어도 거절한다.
- 정규화 후 현재 닉네임과 같으면 사용 가능 확인은 성공하고, 프로필 변경은 닉네임 변경 없음으로 처리하며 새 점유를 요구하지 않는다.

### API 계약

- Web Adapter는 잘못된 닉네임을 공용 Validation Problem Type의 400 Problem Details로 번역한다. 닉네임 중복은 기존 닉네임 충돌 문제 유형의 409 응답을 유지한다.
- 프로필 변경 성공 응답은 실제 저장된 정규화 닉네임을 반환한다. 회원가입과 사용 가능 확인의 정상 응답 구조는 유지한다.

### 호환성

- 기존 DB 닉네임의 일괄 정규화나 충돌 해소는 수행하지 않으며 기존 비정규화 데이터의 후속 조회·갱신 호환성은 보장하지 않는다.
